Change: c2026-10-15-i18n-runtime
Rule: 10-architecture
Summary: Cablear el runtime multiidioma del ERP (castellano default, English, Català),
eliminar literales de UI, migrar todas las vistas/páginas ya generadas a claves i18n,
persistir preferencia de idioma en el usuario, selector de idioma en UI, ficheros
`lang/{es,en,ca}.json` con claves en orden alfabético, y dejar el proyecto listo para
nuevos idiomas y para que cada bloque de desarrollo siga esta lógica.
Goals:
- Idiomas de entrada: Castellano (default), English, Català.
- Cero etiquetas/textos de UI hardcodeados: todo con clave de traducción (front y back
  visibles al usuario).
- Un JSON por idioma: `lang/es.json`, `lang/en.json`, `lang/ca.json` (no partir por
  dominio en este change); claves ordenadas alfabéticamente dentro de cada fichero.
- Migrar **todas** las páginas/UI React (y textos de UI PHP asociados) ya generadas
  (Auth, Partners, Dashboard, legales, flashes, etc.) a claves i18n.
- Selector de idioma en la UI en este change.
- Preferencia de idioma guardada en el usuario (`users` — columna/nombre lo decide
  10-architecture).
- Proyecto preparado para incorporar nuevos idiomas y para actualizar las tres (o más)
  traducciones cada vez que se introduzcan textos nuevos; proceso/norma para bloques
  futuros de desarrollo (canon + rule/skill/CI según decida 10-architecture).
NonGoals:
- Partir traducciones en varios ficheros por dominio (opción descartada: un JSON por
  locale).
- Preferencia solo en sesión o solo por navegador (descartado: preferencia en `users`).
Skills:
- frontend-design
- laravel-specialist
- laravel-patterns
Notes:
- Canon ya exige R-TRV-05 / R-FE-05 (es/en/ca, cero literales); hoy solo existen
  `lang/es.json` y `lang/en.json`, sin `ca`, sin runtime React i18n cableado, y Auth u
  otras pantallas con castellano hardcodeado.
- Templates front ya muestran `react-i18next`; `package.json` / `locales/` pueden no
  estar materializados — 10-architecture elige el cableado conforme a `libraries.md` y
  standards (sin inventar dependencias fuera del canon).
- Relación con `form-input-maxlength`: hilo distinto; este brief es i18n.
- Explore no implementa: la migración de vistas y el cableado van en propose → apply.


## ADDED Requirements

### Requirement: Runtime multiidioma es / en / ca
El sistema SHALL soportar Castellano (default), English y Català. La UI SHALL resolver
textos vía claves i18n, no literales. SHALL existir `lang/ca.json` además de es/en.

#### Scenario: Default castellano
- **WHEN** un usuario no tiene preferencia de idioma o es usuario nuevo sin locale
- **THEN** la aplicación usa castellano como idioma por defecto

#### Scenario: Cambio a en o ca
- **WHEN** el usuario elige English o Català
- **THEN** la UI muestra los textos de ese idioma

### Requirement: Cero literales de UI
Ninguna etiqueta ni texto visible de UI SHALL quedar hardcodeado en PHP o TSX; todo
SHALL usar su clave de traducción.

#### Scenario: Página Auth u otra UI migrada
- **WHEN** se renderiza una pantalla de la aplicación ya migrada
- **THEN** los textos visibles salen de claves i18n (no strings literales de producto)

### Requirement: Ficheros JSON por locale con claves alfabéticas
Las traducciones SHALL vivir en `lang/es.json`, `lang/en.json` y `lang/ca.json`. Las
claves DENTRO de cada fichero SHALL estar ordenadas alfabéticamente.

#### Scenario: Orden de claves
- **WHEN** se añaden o revisan claves en un JSON de idioma
- **THEN** el fichero queda con las claves en orden alfabético

### Requirement: Preferencia de idioma en el usuario
El idioma elegido SHALL persistirse en el modelo User (preferencia en `users`).

#### Scenario: Persistencia
- **WHEN** el usuario selecciona un idioma en el selector
- **THEN** se guarda en su registro de usuario y se reutiliza en sesiones posteriores

### Requirement: Selector de idioma en la UI
La aplicación SHALL ofrecer un selector de idioma en la UI en este change.

#### Scenario: Usuario cambia idioma
- **WHEN** el usuario usa el selector y elige otro idioma soportado
- **THEN** se actualiza la preferencia y la UI refleja el nuevo idioma

### Requirement: Migración de UI ya generada
Todas las páginas/UI ya generadas (Auth, Partners, Dashboard, legales, mensajes flash
de UI, etc.) SHALL migrarse a claves i18n en este change.

#### Scenario: Inventario migrado
- **WHEN** se completa el change
- **THEN** no quedan literales de producto en las vistas/páginas existentes cubiertas
  por el inventario del design/tasks

### Requirement: Listo para nuevos idiomas y nuevos textos
El proyecto SHALL quedar preparado para añadir idiomas nuevos y para exigir/actualizar
traducciones en todos los idiomas soportados cada vez que se introduzcan textos nuevos
(norma + mecanismo que defina 10-architecture: standards, rule/skill, CI).

#### Scenario: Texto nuevo en un bloque futuro
- **WHEN** un desarrollo futuro introduce un texto de UI nuevo
- **THEN** el proceso obligado incluye clave i18n y entradas en todos los idiomas
  soportados (hoy es/en/ca), manteniendo orden alfabético de claves

#### Scenario: Idioma nuevo
- **WHEN** se incorpora un idioma adicional en el futuro
- **THEN** el runtime y la estructura de ficheros permiten añadirlo sin rehacer el
  patrón (detalle en design)
