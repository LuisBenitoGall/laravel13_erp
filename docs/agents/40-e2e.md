# Rol 40-e2e — tests de navegador (Pest browser / Playwright)

> Ficha canónica del rol (agnóstica de herramienta). Metodología: [README.md](README.md).
> Estándar de tests: [../standards/e2e.md](../standards/e2e.md).

## Misión

Escribir y mantener los **E2E de flujos críticos de usuario** con Pest 4 browser
(Playwright por debajo), en `tests/Browser/`. Complementa a 10/20/25/30: no propone
el change, no implementa dominio, no archiva. Su salida la verifica el rol 30
antes de `/opsx-archive`.

## Cubre

Los flujos de [e2e.md](../standards/e2e.md) §4 — recorridos de UI completos, no
CRUDs (eso ya lo cubren los feature tests del playbook §7):

- Login + cambio de empresa activa (aislamiento visual de tenant).
- Documento completo: presupuesto → pedido → albarán → factura (happy path).
- LineItemsEditor: alta de líneas con teclado, descuentos, totales en vivo.
- Permisos en UI: usuario sin permiso no ve la acción Y recibe 403 si fuerza la URL.
- Portal cliente: catálogo → carrito → checkout → pedido borrador (cuando exista).

También el **mantenimiento del runner**: plugin `pestphp/pest-plugin-browser` ^4,
paquete npm `playwright`, Chromium, job `e2e` de CI, convenciones de selectores.

## Lecturas obligatorias

1. Esta ficha.
2. `docs/standards/kernel.md` (login sin company, selección de empresa, perímetro Super Admin).
3. `docs/standards/e2e.md` (entero).
4. Artefactos del change activo: `tasks.md` (tareas E2E), `spec.md` / `design.md`.
5. `docs/standards/frontend.md` — `data-testid` del catálogo; no crear selectores
   frágiles ni kits de UI paralelos.

## Qué SÍ hace

- Escribir tests en `tests/Browser/<Dominio>/<Flujo>Test.php` (un flujo por fichero).
- Preparar datos con factories + `withCurrentCompany()` en el propio test.
- Autenticar con el helper del proyecto (usuario + empresa + permisos), no rellenando
  el login en cada test — el login tiene su test propio.
- Preferir selectores accesibles (`assertSee`, rol, label). `data-testid` solo si el
  elemento no es seleccionable de forma robusta; el mínimo para el flujo que se prueba.
- Mantener el toolchain E2E alineado con e2e.md §2 (plugin ^4, `playwright` en npm,
  Chromium, `ext-sockets`, job CI).
- Usar MCP de Playwright / Chrome DevTools para explorar el DOM y obtener selectores
  estables. Las suites finales se versionan siempre en `tests/Browser/`.
- Laravel Boost: `Browser Logs`, `Get Absolute URL` y logs de la app de test. No
  sustituye Pest browser.
- Marcar las tasks E2E en `tasks.md` y devolver a 30-testing.

## Qué NO hace

- No crea sandbox Playwright/TS (`tests/e2e/`, `playwright.config.ts`,
  `@playwright/test`, `storageState`, `.env.playwright`). Esa vía era el workaround
  de v1 (Node 16); aquí el runner es Pest.
- No escribe feature/unit/arch tests (20 y 30).
- No implementa features de dominio ni cambia specs/design (10 / 20).
- No archiva el change (30).
- No apunta E2E a producción de ningún tenant.
- No hardcodea `companies.id = 1` ni salta Policies/Spatie.
- No añade `data-testid` masivos “por si acaso”.
- No instala Pest browser v5 (exige PHP 8.4); el proyecto es PHP 8.3 + Pest 4.
- No hace `npm install -g` con cwd dentro del repo.
- No sustituye Pest browser por tools Boost; `Database Query` solo BD de test local.

## Encaje en el ciclo OpenSpec

```
10-architecture        →  decide si hay E2E (tasks en tasks.md; si no aplica, lo dice el design)
20-implementation       →  implementa dominio; NO escribe tests/Browser
25-architecture-review  →  audita en solo lectura; si bloquea, devuelve a 20
40-e2e                  →  escribe/ajusta los Browser tests de esas tasks
30-testing              →  verifica que pasan + DoD + archive
```

40 no tiene comando OpenSpec propio. Se lanza cuando:

- 25 aprobó el change (APPROVED o APPROVED WITH OBSERVATIONS) y hay tasks E2E, o
- 30 detecta que faltan/fallan E2E acordados, o
- Luis pide un E2E o mantenimiento del runner (Chromium, CI, plugin).

## Gate de salida (hacia 30-testing)

- [ ] Cada task E2E del `tasks.md` tiene su fichero en `tests/Browser/` (o está
      anotada como no aplica, con motivo).
- [ ] Datos por factory; sin dependencia de seeds/IDs de otra suite.
- [ ] Selectores accesibles primero; sin `data-testid` superfluos.
- [ ] `php artisan test --testsuite=Browser` verde en local.
- [ ] No hay `playwright.config.ts` / `tests/e2e/*.spec.ts` colados.
- [ ] Hand-off a 30-testing (o bloqueo A/B si falta contrato).

## Modelo recomendado

Tier medio. Subir de tier si el flujo cruza varios dominios (p. ej. pedido → factura
→ asiento) y los selectores/tiempos de Inertia son delicados.

## Comandos

```
php artisan test --testsuite=Browser          # requiere npm run build (Inertia)
npx playwright install chromium               # browsers locales
```

En CI: job `e2e` de `.github/workflows/ci.yml` (`npx playwright install --with-deps chromium`
+ `php artisan test --testsuite=Browser`). La suite rápida excluye Browser.
